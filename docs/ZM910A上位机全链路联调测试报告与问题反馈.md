## 一、总体结论

1. **上位机 TCP 底层协议层（`CoordCalibComm`）实现非常规范**：4 字节大端分帧、UTF-8 JSON 编解码、`system.hello` 握手、2s 心跳保活、`system.status` 异步状态同步、左右吸嘴（`Left/R1`、`Right/R2`）14 点自动/手动标定、远程示教、多板检测、真 HALCON Blob 打叉板（`MANUAL_MARK_FOUND`）、空料（`NO_MATERIAL`）、跨 `±180°` 连续 R 轴角度、采图超时预算、并发 `BUSY` 互斥以及硬断线自动重连等核心通信链路**全部实测通畅，无协议报文格式冲突**。
2. **本次联调共发现 4 项上位机侧待修改问题（含 1 项真机上电必死锁问题、2 项高优先级生产异常问题、1 组标定页隐患）及 1 项上机前待确认工艺项**，建议上位机侧在现场联调前优先处理 P0 / P1 项。
3. **视觉工作站侧本次同步发现的 2 项通信边界问题已完成修复并通过回归验证**（见第四节）。

## 二、上位机侧待排查与修改问题清单

### 【P0 · 真机上电必死锁】上位机仍直接独占打开大华相机 `192.168.1.11`

- **涉及位置**：
  - `ZM910A` → `SplashWindow.cs`（约第 137–159 行，开机直接 `global.cameraPallet.OpenCamrea("192.168.1.11", ...)`）
  - `ZM910A` → `CameraHelper.cs` → `IsCameraReady(out string error)`（约第 75–105 行，强检 `global.cameraPallet.m_bIsOpen` 并调用 `GetExposureTime()`）
  - `ZM910A` → `MachineManager.cs` → `Start()`（第 1909 行）、`TriggerTaskPhoto()`（第 4583 行）、`CCDPalletizerThread()`（第 4724 行）
- **问题说明**：
  上位机生产拍照已全部迁移为通过 TCP（`127.0.0.1:9100`）调用视觉工作站，整个 `ZM910A` 中已不再使用 `global.cameraPallet` 执行抓图；但软件启动、自动运行启动以及每次触发拍照前，依然强行连接并校验旧的大华相机句柄 `global.cameraPallet`（`192.168.1.11`）。
- **现场后果**：
  GigE Vision 相机同一时间仅允许单进程以控制模式打开：
  - 若视觉工作站先连接该相机，上位机 `IsCameraReady()` 会报错“摆盘相机未连接或未打开（192.168.1.11）”并禁止启动；
  - 若上位机先打开该相机，视觉工作站将无法连接相机，上报 `cameraConnected = false`，上位机 `IsVisionReadyForProduction()` 同样禁止启动。
  - **两程序同时运行时必然死锁，无法进入自动生产。**
- **建议修改方案**：
  若 `192.168.1.11` 即为交由视觉工作站管理的摆盘相机，请移除 `SplashWindow` 中打开 `cameraPallet` 及 `CameraHelper.IsCameraReady()` 中对 `global.cameraPallet` 的强检（或将其设为仅旧方案启用），统一以 TCP `CalibCommService.Status.CameraConnected` 作为相机就绪依据。

### 【P1 · 高 · 空皮带误停机】开启产品数量校验后，`NO_MATERIAL`（空料）会误触发数量不符暂停弹窗

- **涉及位置**：
  - `ZM910A` → `MachineManager.cs` → `TriggerTaskPhoto()`（约第 4646–4658 行）
  - `ZM910A` → `MachineManager.cs` → `ConfirmVisionProductCount()`（约第 4475–4508 行）
- **问题说明**：
  `TriggerTaskPhoto()` 在收到视觉返回的 `CoordResultList` 后，执行顺序为：
  1. 第 4648 行：先调用 `ConfirmVisionProductCount(list, ref err)`；
  2. 第 4653 行：再判断 `if (num2 == 0) { ... "摆盘相机未检测到物料，按空料结果继续自动流程"; return true; }`。
  当产品档案启用了数量校验（`EnableVisionProductCountCheck = true`，如期望 6 块）且皮带空料返回 `NO_MATERIAL`（`actualCount = 0`，`num2 = 0`）时，第 4648 行会先判定 `0 != 6`，直接执行 `MachinePause(MachineSigType.VISION_PRODUCT_COUNT_MISMATCH, -1400)` 暂停设备并弹窗要求人工确认，导致第 4653 行的空料自动放行分支**完全不可达**，与协议 v1.1 §5.4“空料正常放行、不报警停机”的约定不符。
- **建议修改方案**：
  在 `TriggerTaskPhoto()` 调用 `ConfirmVisionProductCount` 之前，或在 `ConfirmVisionProductCount` 入口处，对 `string.Equals(list.VisionErrorCode, "NO_MATERIAL", StringComparison.Ordinal) && (list.List?.Count ?? 0) == 0 && list.InvalidBoardCount == 0` 直接放行继续空料流程。

### 【P1 · 高 · 双端协同风险】上位机不传 `expectedCount`（=0）时，多板场景可能静默截断漏取（实弹复现）

- **涉及位置**：
  - `ZM910A` → `CameraHelper.cs` → `InspectVision()`（第 163 行：当 `EnableVisionProductCountCheck == false` 时传 `expectedCount = 0`）
  - `Seprays.VisualInspectWpf` → `CalibrationCtl.cs` → `Test()`（第 1836 行：固定传 `expectedCount = 0`）
  - `Seprays.VisualInspectWpf` → `CoordCalibComm.cs` → `Inspect()`（第 283 行：`expectedCount <= 0` 时在 JSON 中省略该字段）
- **实测复现现象（T16B）**：
  - 当上位机省略 `expectedCount` 时，视觉端按协议 v1.1 §5.4 兜底使用视觉工作站本地 `ExpectedBoardCount`（默认 6），并出于 HALCON 性能与超板数保护将最大匹配数设为 `NumMatches = expectedCount + 1 = 7`。
  - 实测皮带有 **8 块板** 且上位机关闭数量校验（省略 `expectedCount`）时：视觉端最多只匹配 7 块（**截断丢失第 8 块板**）并返回 `errorCode = BOARD_COUNT_MISMATCH, coordinateMapped = true`；上位机 `UsableForProduction` 为 `true`，且 `ConfirmVisionProductCount` 因未开启数量校验直接返回 `true` 放行。
  - **结果：设备无任何报警，静默漏取第 8 块板留在皮带上。**
- **建议双端对齐方案（二选一）**：
  - **方案 A（推荐，最稳妥且符合 v1.1 规范）**：上位机调用 `Inspect()` 时**始终传入产品档案中的实际预期板数**（`ExpectedVisionProductCount`），`EnableVisionProductCountCheck` 开关仅控制上位机收到结果后是否弹出数量不一致确认框。
  - **方案 B**：若上位机确实希望在关闭数量校验或标定页点击“测试”时不传 `expectedCount`，双方约定省略 `expectedCount` 表示“不限板数/不校验数量”，视觉端再据此放开 `NumMatches` 上限并不报 `BOARD_COUNT_MISMATCH`。请回复确认采用方案 A 还是方案 B。

### 【P2 · 中】标定页面 `CalibrationCtl` 交互与安全隐患

1. **点击“取消标定”未下发停轴，且存在 UI 线程 3 秒死锁风险**
   - **位置**：`CalibrationCtl.cs` → `Cancel()`（约第 1795–1813 行）、`MoveXYR()`（约第 1937 行）、`WriteMessage()`（约第 2481 行）。
   - **问题**：
     - `Cancel()` 只向视觉发送了 `calibration.cancel`，未调用 `_motion` 停止正在运动的 X/Y/R 轴，取消后当前运动仍会走完目标点。
     - `Cancel()` 在 WPF UI 线程上同步阻塞等待 `_calibComm.CancelCalibration(...)`（最长 3000ms）；若此时后台线程中的 `MoveXYR()` 运动报错并调用 `WriteMessage()`（内部为同步 `Dispatcher.Invoke`），将与 UI 线程互相等待直至 3 秒超时。
   - **建议**：取消标定时先停止对应运动轴，并将 `CancelCalibration` 放到后台线程异步执行（同时 `MoveXYR` 异常处理改用异步 `PostMessage`）。

2. **标定拒动错误码未按协议 v1.1 §6.4 细分**
   - **位置**：`CalibrationCtl.cs` → `OnCalibrationMoveRequest()`（约第 2357–2374 行）。
   - **问题**：任何运动或读轴失败均固定上报 `SERVO_ALARM`，未区分 `SOFT_LIMIT`、`EMERGENCY_STOP`、`SETTLE_TIMEOUT`。
   - **建议**：根据运控错误码映射为规范中对应的 `code`，方便视觉界面与现场日志快速定位拒动原因。

3. **双击测试结果列表移动后，手动点动按钮永久被禁用**
   - **位置**：`CalibrationCtl.cs` → `MoveXYR()`（第 1860 行）与 `DataGridPoint_MouseDoubleClick()`（第 2269 行）。
   - **问题**：`MoveXYR()` 入口将 `AxisMoveEnabled = false`，但缺少 `finally` 恢复逻辑。在非标定状态下双击点位表走位后，手动点动区将一直保持禁用。

4. **视觉工作站 IP/端口硬编码**
   - **位置**：`SplashWindow.cs:172`、`MainWindow.cs:422`、`MainViewModel.cs:1128` 均硬编码 `127.0.0.1:9100`。建议后续改为可读取系统配置项，避免端口冲突时必须重编译上位机。

5. **（顺带发现的非通信 Bug）标定页手动点动轴等待句柄写错**
   - `CalibrationCtl.cs` 中 `RotateLeft2` / `RotateRight2`（第 1380、1399 行）移动的是 `R2Index`，但等待到位写成了 `WaitAxis(RIndex)`；
   - `Z1Up` / `Z1Down` / `Z2Up` / `Z2Down`（第 1456、1475、1494、1513 行）移动的是 `Z1Index` / `Z2Index`，但等待到位均写成了 `WaitAxis(BeltIndex)`。

## 四、视觉工作站侧本次同步修复记录

在本次实弹全链路联调中，视觉工作站侧同步检出并修复了以下 2 项边界问题：

1. **单客户端连接平滑替换（v1.1 §2.1）**：
   - 修复前：`TcpVisionServer` 在已有活跃连接时会直接拒断新接入连接；若上位机异常重启或发生网络半开闪断，需等待旧连接 6 秒心跳超时才能重连。
   - 修复后：新连接接入时由服务端立即平滑关闭旧连接并接管新连接，同时保持严格 `ConnectionId` 隔离与旧标定会话安全中止，杜绝跨连接串包（`T18` 复测通过，并已加入工作站内置 `CommunicationSelfTest`）。
2. **`calibration.cancel` 与同步匹配失败/求解并发竞态**：
   - 修复前：若上位机下发 `calibration.cancel` 时视觉恰好在同步 HALCON 匹配中返回 `MATCH_FAILED` 或进入求解，回传的 `calibration.completed` 未携带取消请求的 `correlationId`，导致上位机 `CancelCalibration` 阻塞 3000ms 超时。
   - 修复后：采点后与求解提交前检查取消状态，且 `SendCompletedOnceAsync` 在存在挂起 `CancelCorrelationId` 时统一回填关联 ID，并同步清理会话关联表 `_calibrationRequestConnections`（`T24` 复测秒级返回，不再超时）。
